# V10 Error-Conditioned Semantic Correction

## Objective

V10 tests whether a small, high-precision correction layer can recover semantic
SQL failures without modifying correct queries. It retains the frozen V9 scoped
evidence generator and Arctic Q4 candidate path. It does not add probes,
multi-candidate generation, Talon, reinforcement learning, external APIs, or
generator fine-tuning.

The intended runtime is:

```text
question + schema + scoped evidence
                 |
              Arctic Q4
                 |
           candidate SQL
                 |
      high-precision error detector
         |                    |
      abstain          localized repair
                              |
                       safe re-execution
```

## Dataset roles

- **Error memory:** BIRD training cases and execution-changing synthetic mutations.
- **Calibration:** 40 inspected V8/V9 cases plus 30 BIRD-training natural-error captures.
- **Fresh pilot:** 40 cases frozen with seed `20260917` before correction development. Their question groups do not overlap prior V7-V9 prediction captures.
- **Regression:** previously inspected V5-V9 cases.
- **Locked final:** the 1,033-case V6 final remains unopened.

Expected SQL and results remain inside scoring and mutation-building code. Runtime
records contain schema-independent signatures and minimal patch descriptions,
not raw gold SQL.

## Error memory

The memory builder creates result-changing hard negatives for four families:

| Family | Localized difference |
|---|---|
| Operation | aggregate added, removed, or replaced |
| Grain | grouping removed or changed |
| Predicate | column, operator, literal, or predicate changed |
| Join | join removed, added, or replaced |

Identifiers are canonicalized into roles and the retrieval signature combines
question intent, evidence roles, SQLGlot AST shape, and bounded result shape.
Only mutations whose execution differs from the source query are retained.

## Detection and repair

The detector asks whether one known error family is present. It does not estimate
whole-query correctness. Each family is calibrated independently and may affect
a query only at precision of at least 0.80 with sufficient support and no
unacceptable correct-query regressions.

Repairs are deterministic SQLGlot subtree edits where possible. A patch is
rejected if unrelated AST components change, if the query fails the unchanged
security policy, or if execution fails. Numeric-only literal remapping abstains
because its value-to-column binding is ambiguous without stronger evidence.

The optional Qwen corrector is gated behind calibrated, unpatched fresh-pilot
errors. It is not a generic second generation call.

## Frozen pilot gates

The 40-case pilot requires all of the following before a broader campaign:

- EX lift of at least 0.075 over Arctic scoped evidence;
- at least three net corrections and no more than one correct-query regression;
- detector precision of at least 0.80;
- repair success of at least 0.50 on attempted wrong queries;
- completion of at least 0.95;
- p95 latency below 20 seconds;
- no database byte changes.

Failure stops selective Qwen correction, broader development evaluation, and any
locked-final proposal. Qwen V5 remains the application default until a candidate
passes comparable evaluation.

## Trust boundaries

All database access uses the existing read-only URI, SQLite authorizer, SQLGlot
statement validation, deadlines, result-width, row, and byte limits. Attachments,
extensions, writes, and changing-time functions remain denied. Error examples,
schema descriptions, values, and model output are untrusted. API cost is fixed at
zero dollars.
