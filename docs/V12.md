# V12: value-grounded schema notes and SQL conventions

Frozen on 2026-09-14, before any V12 model run.

## Motivation

The [V5 failure audit](V5-FAILURE-AUDIT.md) found that the largest fixable model weakness is grounding in stored values (18 of 49 model errors), followed by prompt-addressable conventions: query logic, duplicate rows, and extra columns (22). The V5 prompt shows column names and types only. BIRD's `database_description` files and the database's stored values are not supplied.

## Hypothesis

Adding compact column notes and a short list of SQL conventions improves execution accuracy of the unchanged Qwen2.5-Coder 7B pipeline, without weakening any security control.

## Arms (identical except for the prompt)

| Arm | Model profile | Schema text | System rules |
|---|---|---|---|
| Control | `qwen_v5` | V5 DDL (frozen V10 control settings) | V5 |
| Rules only | `qwen_v12_rules` | V5 DDL | V5 + V12 conventions |
| Notes only | `qwen_v12_notes` | V5 DDL + column notes | V5 |
| Full | `qwen_v12` | V5 DDL + column notes | V5 + V12 conventions |

All arms share these settings:
- model `qwen2.5-coder:7b-instruct`, served through Ollama with the model digest recorded
- full schema mode, value probes, direct prompt style
- one generation strategy, V5 correction budget
- the read-only execution policy with a 10-second deadline

**Column notes** (`sql_agent.v12_notes`, version `sql-v12-column-notes-v1`), one line per column with any of:
- the BIRD column and value description
- up to three stored example values for text columns
- storage-format tags for text columns holding numbers, money, percentages, dates, or times, taken from the bounded read-only value profile

Notes are capped at 6,000 bytes and ranked by storage-format tags and question-term overlap. They are derived from database files only; reference SQL is never used.

**V12 conventions** (appended to the frozen V5 system prompt, which already asks for requested columns only and `LIMIT` only when requested):
1. Clean text-stored numbers, money, counts, and durations with `REPLACE` and `CAST` before comparing, sorting, or doing arithmetic.
2. Write literal values exactly as stored (case, abbreviations, accents), as shown in column notes or value hints.
3. Use `DISTINCT` when listing entities that can repeat through joins.
4. Use `CAST(... AS REAL)` for division and percentages.
5. Exclude `NULL`s when ordering to find a highest or lowest value.

The V12 profiles run through the same frozen V5 generation path as the control, so the correction loop (up to three attempts), JSON output schema, value hints, and coverage checks are identical across arms.

The conventions come from failure patterns on BIRD **training** databases (the V5 holdout). V12 is evaluated only on BIRD **dev** databases, so selection and testing never touch the audited cases.

## Data

- **Development selection:** V6 development split, 200 inspected cases from the 11 BIRD dev databases. It was previously exposed in V6/V7 and is used for selection only.
- **Final:** V6 locked holdout, all **1,033** question-disjoint BIRD dev cases (hash `08e4ff1c…`), opened for the first time in V12 and exactly once, after the development selection is frozen.

## Frozen gates

**Development selection:** run all four arms on the 200 development cases. The winner is the V12 arm with the highest execution accuracy (`execution_accuracy_v7`) that satisfies all of:
- EX at least control + 0.03
- completion no more than 0.02 below control
- p95 latency at most 2× control
- zero database byte-hash changes

If no V12 arm qualifies, V12 stops: no final is run and V5 remains the default.

**Final promotion:** run control and the frozen winner once on the 1,033 locked cases. Promote only if all hold:
- paired database-grouped EX delta at least +0.03, with 95% bootstrap interval lower bound above 0
- completion no more than 0.02 below control
- p95 latency at most 2× control
- zero database byte-hash changes
- official gold self-consistency at least 0.99

Official set-based scorer agreement is reported alongside.

## Runtime and cost

Arms run on Modal A10G GPUs (owner decision: the local GPU was occupied). Each container runs Ollama and the unchanged `sql_agent` pipeline together, because the Ollama client accepts only localhost. The 11 public BIRD dev databases and their `database_description` folders are uploaded. Frozen case files keep their Windows database paths; each container links those exact path strings to the uploaded copies, so no dataset file is rewritten and fingerprints are computed from real database bytes. Control and candidate always run on the same runtime; V12 numbers are never compared with local V5 numbers.

- **Cloud spend cap:** $15.
- **Stays unchanged:** no API model, no security-policy change, no reference SQL in prompts.
